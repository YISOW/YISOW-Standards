# YISOW Application Development & Distribution Standard

**规范编号：** YISOW-ADS-001\
**正式版本：** V1.4\
**生效日期：** 2026-10-12\
**适用平台：** Windows / macOS / Android\
**分发模式：** 独立分发优先\
**规范状态：** 正式生效

本规范完整替代 YISOW-ADS-001 V1.3 及更早版本，成为 YISOW 应用开发、产品质量、测试验收与独立分发的唯一现行通用基准。

本规范仅管理产品与工程质量。Codex 智能体行为、授权、Git 操作等由独立的 ADS-002 及用户明确指令管理。

---

# 第一章：基本原则

## 1.1 开发目标【强制】

所有 YISOW 应用必须追求：

**功能真实、原生体验、代码精简、质量可验证、数据安全、长期可维护。**

禁止将工程骨架、编译成功、模拟数据演示或未验证功能直接视为正式完成品。

## 1.2 优先级【强制】

发生冲突时：

1. 法律及平台强制安全、技术约束。
2. 用户当前项目的最新明确要求。
3. 当前项目已确认且仍有效的决策和兼容性要求。
4. 本规范。
5. AI 自行提出的建议。

具体项目要求不得无故扩展为全局规则。

规范中的【强制】必须执行；【默认】可被明确的项目要求覆盖；【按需】仅在适用时执行。

对于无法满足的强制要求，应如实标记为未完成、失败或未验证，不得声称已经符合。

# 第二章：开发前的核心风险验证【强制】

在开展大型工程实现之前，必须识别项目的核心失败风险。

根据项目性质，优先检查：

## 2.1 数据与外部能力可用性

- 关键数据源、接口和权限是否真实可用。
- 是否能够合法、稳定地获得所需信息。
- 必要的账号验证、网络连接及设备权限是否可完成。
- 如果依赖第三方服务，是否存在无法满足的访问限制。

不得用模拟数据证明真实数据功能已经完成。

## 2.2 核心技术及效果可行性

- 关键算法或模型是否能够真实运行。
- 其输出是否基本满足产品的核心需求。
- 目标设备是否具有必要的性能、内存及兼容性。
- 关键技术的缺陷是否有可行解决路径。

## 2.3 构建与交付环境

- 必要的 SDK、编译器、运行时及依赖是否可用。
- 是否能够为目标平台生成可运行构建。
- 是否能够在目标设备或相应测试环境启动。

对于直接影响核心功能的沙盒、文件权限、密钥存储、登录会话、数据目录或系统安全限制，应尽早在具有代表性的真实执行环境中验证，而非仅在权限条件不同的开发环境中验证。

存在关键风险时，优先制作最小技术验证程序。

不要求每个项目都验证上述所有内容，只验证影响该项目核心可行性的部分。

如暂时无法取得真实环境，可以进行明确标识的替代验证，但不得将其描述为目标环境已经通过。

核心风险未解决时，不应继续大规模堆积依赖该风险的界面与外围功能。

# 第三章：开发阶段与真实业务闭环【强制】

## 3.1 最小可运行闭环

项目应尽早建立一个真实、可运行、可验证的核心功能闭环。

例如：

- 监控 App：真实登录或授权 → 取得真实数据 → 正确展示。
- 超分 App：导入真实图片 → 模型处理 → 输出图片 → 检查实际质量。
- 翻译 App：加载真实模型 → 输入文本 → 推理翻译 → 显示结果。
- 文件传输 App：选择文件 → 实际传输 → 接收与保存 → 在目标端完成所要求的读取或预览。

最小闭环不要求完成全部产品功能，但必须实际完成其声称实现的业务流程。

**闭环的完成位置必须与所声明的功能一致。**

例如，声称文件已成功接收，可以提供接收与完整性证据；声称文件能够预览，则必须验证实际 App 中的预览过程。不能以其中一个环节通过代替后续环节。

## 3.2 增量开发

优先采用：

**核心风险验证 → 最小闭环 → 分阶段扩展 → 完整验收 → 正式发行。**

每个主要阶段应有明确的可验证结果。

不得长期只开发 UI、配置页面和模块骨架，而把核心功能验证全部留到最后。

涉及目标设备运行的项目，应在适当阶段生成实际可安装、可启动的测试版本。

## 3.3 阶段完成标准

一个阶段只有在相关条件得到验证后才能宣布完成：

- 对应功能已经真实实现。
- 适用的构建可以运行。
- 核心输入和输出符合要求。
- 主要错误路径得到合理处理。
- 未引入已知的严重功能回归。

如果只完成了其中部分内容，应如实标明完成范围。

**必须区分模块完成、用户可操作的业务功能完成、整体产品完成与正式发行完成。**

底层模块可以作为独立的已完成研发里程碑，但不得由此推定尚未接入的用户界面、跨端链路或发行流程已经完成。

# 第四章：核心功能效果验收【强制】

## 4.1 功能正确不等于效果合格

核心业务质量必须根据产品目标进行验证。

不能用编译通过、单元测试通过、界面可操作或者算法成功执行代替真实效果验收。

## 4.2 验收样本

对质量敏感的功能，应建立具有代表性的测试样本。

根据功能选择合适指标，例如：

- 图像处理：整体清晰度、细节真实性、人脸、复杂纹理及失真。
- 语音翻译：准确性、完整性、延迟、实时稳定性。
- 数据监控：真实数据准确性、更新状态及异常处理。
- 文件传输：文件完整性、断点续传、错误恢复。
- 本地 AI：输出质量、推理速度、内存与资源占用。

不强迫不同产品采用统一的数值指标。

**样本代表性不仅包括输入内容，也包括与验收目标有关的处理路径及运行环境。**

直接调用底层 API 的样本测试，不能自动证明包含转换、存储、解密、导出、播放或其他步骤的完整用户路径已经通过。

对无法仅靠数字判断的视觉或语言质量，应使用实际样本进行人工评估，必要时由用户确认。

### 主观效果验收原则

优先利用代表性真实样本、可比较结果及实际产品使用路径进行验证。

以下情况应请求用户确认：

- 核心功能出现重大质量变化。
- 结果存在明显的主观争议。
- 可用证据不足以支持质量达标结论。
- 质量取舍会明显影响用户此前确认的目标。

一般的小幅效果调整，不要求每次都由用户亲自验收。

不能因为没有要求用户确认，就自动认定主观效果已经达标。

## 4.3 对照与回归

优化现有功能时，应尽可能使用相同测试样本比较修改前后的结果。

必须检查：

- 目标问题是否改善。
- 其他重要质量维度是否退化。
- 性能或资源占用是否产生不可接受的代价。

局部改善不能自动视为整体改善。

不得为追求单一指标而忽略用户实际使用效果。

# 第五章：问题修复与开发路径纠正【强制】

遇到持续失败或反复修改无效时：

1. 先分析实际问题与可验证的原因。
2. 明确本次修改针对什么问题。
3. 采用尽可能小的修改进行验证。
4. 与修改前的结果对比。
5. 无改善时重新评估方向，而不是继续叠加补丁。

同一技术路径连续多次不能产生实质改善时，应停止无依据的重复尝试，重新检查前提、算法、数据、依赖或架构。

必要时向用户说明：

- 原技术路径存在的问题。
- 建议替代方案。
- 可能产生的影响。

重大架构调整按照项目已有的授权规则执行。

# 第六章：品牌、语言与版本【强制】

## 6.1 品牌

统一使用 YISOW 作为版权品牌。

在设置或关于区域底部显示：

**© 2026 YISOW. 保留所有权利。**

根据界面语言提供相应译文，并按实际维护情况更新版权年份。

## 6.2 语言

Windows、macOS、Android 新项目至少完整支持简体中文与英文。

默认跟随系统语言，不支持时回退英文。

设置中允许选择：

- 跟随系统。
- 简体中文。
- English。

用户手动选择优先并持久保存。

包括错误信息、权限说明、安装程序和更新日志在内的适用用户可见内容均应本地化。

## 6.3 版本

默认采用 Major.Minor.Patch 版本规则。

程序、安装包、系统元数据、更新日志和发布说明应使用一致的版本信息。

保持 Windows 安装身份、macOS Bundle Identifier、Android applicationId 等稳定。

# 第七章：原生 UI 与平台技术【强制默认】

## Windows

- 优先 Windows App SDK + WinUI 3。
- 遵循 Fluent Design。
- 支持主题、DPI、多显示器、快捷键和无障碍。
- 普通主程序默认不以管理员权限运行。

## macOS

- 优先 SwiftUI，按需结合 AppKit。
- 遵循 Apple Human Interface Guidelines。
- 使用原生菜单、窗口、设置和系统材质。
- 适用时遵循系统的 Liquid Glass 设计。

## Android

- 优先 Kotlin + Jetpack Compose。
- 默认原生 Material 3。
- Liquid Glass 仅在项目明确要求时启用。
- 遵循系统权限、生命周期、手势导航及无障碍规范。

既有合理架构不因默认技术选型强制重写。

跨端产品保持业务规则、数据格式和产品身份一致，但不强制三端界面完全相同。

所有正式界面控件应具有实际功能，不得保留未说明的假交互。

# 第八章：安装、升级与独立分发【强制】

不默认面向 Microsoft Store、Mac App Store 或 Google Play 上架。

本章区分开发与内部测试产物、阶段性可运行候选，以及正式公开发行产物。

开发候选可以尚未满足所有正式发行条件，但必须准确标识其实际构建、签名、测试和可用范围，不得称为已经完成正式发行验收。

## 8.1 Windows

默认使用 Inno Setup 生成 EXE 安装器。

使用传统完整向导：

**语言 → 欢迎 → 安装范围 → 安装路径 → 附加任务 → 确认 → 进度 → 完成。**

- 默认所有用户安装，按需请求 UAC。
- 允许技术上可行的当前用户安装模式。
- 默认目录为 `%ProgramFiles%\YISOW\AppName`。
- 允许修改安装位置。
- 默认创建开始菜单快捷方式。
- 桌面快捷方式和开机自启默认关闭。
- 提供标准卸载入口。
- 支持旧版本识别与兼容覆盖升级。
- 避免无意重复安装和降级。

### Windows 代码签名

正式独立分发应评估代码签名、可信发布者身份及 Windows SmartScreen / Smart App Control 等实际信任风险，优先采用有效的可信签名方案。

**Windows 代码签名不在本规范中被规定为所有发行场景一律适用的独立硬阻断条件。**

未签名时必须：

- 如实披露未验证发布者及相关安全提示风险。
- 不得宣称程序已通过可信代码签名验证。
- 不得伪造 UAC 中的已验证发布者身份。

如果法律、目标环境的安全政策或当前项目明确要求有效签名，则必须按该要求验收。

## 8.2 macOS

普通 App 默认使用 DMG 拖入 Applications 安装。

正式外部分发采用 Developer ID 签名、公证以及必要的完整性验证。

需要系统级安装组件时才评估 PKG。

开发签名或尚未公证的内部候选，不得被表述为已完成正式外部分发验证。

## 8.3 Android

默认生成正式签名 APK。

保持包名、版本号和签名升级兼容。

保护 Release Keystore，按正式独立分发时适用的政策处理开发者验证。

Debug APK 可以用于开发验证，但不能冒充正式签名发行包。

## 8.4 共同要求

目前不开发应用内自动更新。

支持用户手动安装新版，确保数据兼容。

公开发布应附带版本、架构、更新说明、必要安装指引和 SHA-256 校验信息。

开发候选的构建或安装结果，不自动证明正式发行包的签名、完整性、安装或升级路径已经通过。

# 第九章：系统身份与图标【强制】

所有正式应用必须正确显示：

- 产品名称。
- 图标。
- 版本。
- 适用的发布者信息。

## Windows

检查 EXE、安装器、卸载器、窗口、任务栏、快捷方式、开始菜单及已安装应用列表。

正确配置版本资源及适用的 AppUserModelID。

UAC 的已验证发布者必须来自真实有效的代码签名身份，不得以安装器字符串伪装。

安装器提权不意味着主程序可以无故提权。

## macOS

检查 Finder、Dock、Launchpad、Spotlight、DMG 和 Bundle 元数据。

## Android

检查 Launcher、Adaptive Icon、最近任务、通知及启动入口。

不得遗留默认模板图标、错误名称及测试占位资源。

# 第十章：更新日志与用户数据【强制】

## 10.1 更新日志

新版本首次启动时自动展示一次 What's New，并保存已展示版本记录。

设置中保留历史更新入口。

两者使用统一的更新日志数据源。

## 10.2 数据安全

用户数据与程序安装文件合理分离。

升级时保护用户设置、文件及数据库。

涉及数据库结构变更时应考虑迁移、备份及失败恢复。

普通桌面卸载默认保留用户数据。

Android 遵循原生卸载机制，重要数据按项目需求提供导出或备份。

采用最小权限原则，不硬编码凭据，不在日志中泄露敏感信息。

# 第十一章：项目连续性与资产保护【强制】

长期项目必须维护可持续读取的项目记录。

默认包括：

- `PROJECT_CONTEXT.md`：项目现状。
- `DECISIONS.md`：已确认及否决的决策。
- `ASSET_MANIFEST.md`：资源及确认状态。
- `DEVELOPMENT_LOG.md`：修改、问题和进度。

小项目允许合并文件。

资产必须区分：

- **Approved：** 已确认。
- **Proposed：** 候选。
- **Rejected：** 已否决。

已确认的图标、Logo、设计和核心资产不得擅自替换；已否决方案不得误当作正式资产。

## 11.1 已批准资产变更保护

**修改已确认的产品名称、品牌身份、图标、核心设计或其他重要资产之前，必须核对当前可访问的有效批准决策和对应资源。**

当前对话未出现某项资产，不等于该资产不存在或此前未获批准。

已有批准依据无法可靠取得时，应保留现有资产与身份，不得擅自使用重新生成的方案替代。

后续整改可以修复违规结果，但不应抹除已经确认的历史违规事实。

## 11.2 项目状态连续性

在恢复项目、进入重要开发阶段、重大修改、安装打包和发行前，复核项目档案及可访问的历史要求。

**长期项目的当前事实应有明确的权威恢复入口。**

各档案可以分别记录决策、资产、历史和当前状态，但不应在多份文件中重复维护相互独立的即时版本及验收结论。

本要求不增加固定的额外档案数量，不要求每次局部修改全量查阅历史。

重要阶段结束后更新项目交接记录。

不得声称已经访问不可读取的历史对话或资源。

---

# 第十二章：代码精简与安全清理【强制】

## 12.1 代码质量

- 采用清晰的模块边界。
- 避免重复逻辑与补丁堆积。
- 控制不必要的依赖。
- 删除确认无引用的遗留代码。
- 不为了微小需求引入复杂架构。
- 保持合理的性能、内存和安装包体积。

发现明显技术债时，可以向用户提出有具体依据的重构建议。

重大重构不得擅自实施，需保护已有功能、数据及批准资产，并进行回归验证。

## 12.2 开发临时文件清理

在阶段完成后，检查并清理本项目产生的、已确认无用且能够安全再生的临时文件。

不得擅自删除：

- 源代码和未提交修改。
- 用户真实数据。
- 项目档案及已批准资产。
- 数据库、备份和重要测试样本。
- 签名证书、密钥和 Keystore。
- 正式发布产物。
- 高成本模型和共享资源。
- 项目之外或来源不明的文件。

禁止未经范围确认的大规模破坏性清理。

不确定时保留，必要时请求用户决定。

# 第十三章：验证与异常报告【强制】

## 13.1 验证范围

根据项目性质进行：

- 构建环境与真实运行验证。
- 核心业务端到端验证。
- 实际效果与性能验证。
- 安装、升级、签名及卸载验证。
- 图标、名称及系统身份验证。
- 中英文、主题、权限与错误处理验证。
- 数据保护及功能回归验证。
- 已确认设计、资产及项目约束复核。

尽可能使用真实设备、真实输入和独立测试环境。

没有真实验证条件时，应明确区分模拟测试和实际测试。

### 验证证据适用范围

**关键验证结论必须能够对应其实际对象与范围：**

- 被验证的代码状态、构建版本或具体发行产物。
- 实际使用的平台、设备及运行环境。
- 覆盖的功能、输入、用户路径和结果。
- 与真实产品使用路径存在的重要差异。

可引用已有构建记录、测试结果或报告，不要求为每项验证新增独立文档。

旧验证证据仅在相关实现、配置、资源和环境条件仍然适用时复用。

发生改变时，根据实际影响补充相关验证，不要求机械重跑全部测试。

不能将旧构建、模拟器、接口夹具或底层模块的成功，直接用于证明未覆盖的新构建、真机、实际用户路径或完整产品已经通过。

## 13.2 验收状态

只有三种有效结论：

- **通过：** 有实际验证依据。
- **失败：** 已证实不满足要求。
- **未验证：** 缺少必要的环境、数据、设备或测试证据。

不得将编译通过等同于核心功能通过。

测试工具或夹具自身出错时，该项测试不得视为通过；也不得在没有独立产品证据的情况下直接认定为产品失败。

运行环境受阻、权限条件不足或测试中断，应按实际影响保留未验证状态。

若已有独立证据证明产品本身存在缺陷，测试工具的其他错误不能抹除该缺陷。

对已经观察到的问题，只有证据充分时才能确认根因；缺少根因证据时可确认故障现象，但不得将猜测写为定论。

### 问题归因

分析项目复盘、缺陷及验收结果时，应区分：

1. **执行违规：** 已有明确规范却没有遵守。
2. **规范歧义：** 规范要求存在适用范围或判断标准不清的问题。
3. **产品未完成：** 对应功能或发行工作尚未完成。
4. **尚未验证：** 证据不足，暂不能确认通过或失败。

同一问题可以涉及多个类别，但不得把产品未完成或尚未验证直接等同于违规，也不得用规范歧义掩盖已有明确要求的执行失败。

## 13.3 异常导向报告

向用户默认只报告：

1. 正式发布阻断项。
2. 已确认问题及其影响。
3. 关键未验证风险。
4. 需要用户决定的重要冲突。

正常通过的检查不逐项报告。

问题应尽量包含原因、影响、当前状态及建议处理方式。尚未查明原因时应明确标记，不得编造。

不存在需要报告的异常时，仅说明：

**“本轮在已执行的验证范围内未发现问题。”**

## 13.4 发布门禁

核心功能未达到已确定的验收标准、无法生成实际发行构建、关键安全要求不满足或存在严重数据丢失风险时，不得宣称正式发行已通过验收。

**验收结论必须对应实际声明的交付范围：**

- **开发测试构建：** 只声明已经验证的研发与测试成果。
- **阶段性功能或候选产品：** 可以在已验证范围内宣布阶段完成，但不得冒充完整产品。
- **正式公开发行：** 必须满足对应平台、目标用户及当前项目实际适用的发行、安全、安装、升级和核心质量要求。

Windows、macOS、Android 的签名及公证义务按第八章和适用平台要求分别判断，不得套用已经被替代的旧版本硬阻断条款。

普通功能缺陷根据严重程度处理，不将所有轻微问题机械地定义为阻断项。

对于未验证的关键条件，应保留待验证状态，而不是虚构测试通过。

# 第十四章：开发助手执行流程

## 14.1 新项目

1. 识别目标平台、核心业务和现有约束。
2. 先验证关键数据、算法与构建风险。
3. 建立最小真实业务闭环。
4. 分阶段实现功能，并验证真实效果。
5. 维护项目档案及已确认资产。
6. 保持代码精简和数据安全。
7. 构建安装包并执行适用验收。
8. 安全清理无用临时产物。
9. 仅向用户报告异常与关键风险。

## 14.2 现有项目

1. 先读取现有项目档案与有效决策。
2. 检查原功能和核心质量基准。
3. 识别真实问题，进行针对性修改。
4. 用相同或可比较的样本验证改善。
5. 防止新修改引发回归。
6. 更新项目记录。
7. 完成适用测试和安全清理。

## 14.3 执行边界

本规范定义产品及工程质量要求。

具体 Codex 智能体的授权范围、重大修改审批、Git 提交权限等，由用户明确指令及适用时已正式生效的独立执行规范管理。

未生效的 ADS-002 审阅稿不得被当作已授权的执行规则，也不因本规范修订而自动生效。
